# D21-C — RPC Governance Inventory (Automated)

Status: **Active — regenerated by CI**
Owner: Platform Security
Opened: 2026-07-01
Precedes: D21-A (partition RLS atomicity), D21-B (RLS coverage gate)

## Purpose

Transform the manual inventory work of D20-A and D20-D into a **consumable
governance artifact** that the pipeline regenerates automatically. A future
audit should read this report — not re-run weeks of investigation.

## Consumable columns

Every `SECURITY DEFINER` function in the `public` schema is listed with:

| Column         | Source                                                                 |
|----------------|------------------------------------------------------------------------|
| RPC            | `pg_proc` (name + identity args)                                       |
| Owner          | `pg_authid` via `proowner` — guarded by `assert_security_definer_owner` |
| Definer        | Always `SECURITY DEFINER` (scope of this inventory)                    |
| Grants         | `aclexplode(proacl)` — comma-separated roles with EXECUTE               |
| Tenant Guard   | Heuristic over `prosrc` — one of `assert_caller_tenant / active_tenant / auth_uid / none` |
| auth.role      | `checked` if body references `auth.role()` / `auth.jwt()`               |
| Consumers      | Count of frontend/edge/e2e/tests/contracts files calling the RPC       |
| Status         | Deterministic classification (see below)                                |

Machine-readable copy lives at
`docs/audits/active/d21-c-rpc-governance-inventory.csv` — same columns plus
`source_hash` (md5 of `prosrc`) so week-over-week drift is trivial to diff.

## Status rules (deterministic)

| Status | Trigger                                                                   |
|--------|---------------------------------------------------------------------------|
| RISK   | Grants include `PUBLIC` or `anon` **AND** `tenant_guard = none`           |
| WATCH  | Grants include `PUBLIC`/`anon` with a guard present, OR wide-granted RPC with 0 consumers |
| OK     | Grants scoped to `authenticated`/`service_role` **AND** `tenant_guard ≠ none` |
| INFO   | Everything else (postgres-only, service_role-only, internal helpers)      |

No editorializing — a function's status is a pure function of its grants,
body, and consumer count. Human review reads the report and decides what to
promote to a hotfix; the pipeline does not open findings on its own.

## Pipeline

`.github/workflows/rpc-governance-inventory.yml`

- **Triggers**: PRs touching migrations/functions/reports, pushes to `main`,
  weekly cron (Mondays 04:17 UTC), and manual dispatch.
- **Output**: uploads `.md` + `.csv` as artifact `rpc-governance-inventory`
  with 90-day retention.
- **Enforcement**: the job **fails** if any RPC is classified `RISK`.
  `WATCH`/`OK`/`INFO` do not fail — they are governance signal, not gates.

## Files

- `tools/reports/rpc_governance_inventory.sql` — canonical query, TSV output.
- `tools/reports/generate_rpc_governance_inventory.py` — runs psql, scans
  consumers, classifies, writes Markdown + CSV.
- `.github/workflows/rpc-governance-inventory.yml` — CI wrapper.

## Scope discipline (per authorization)

- Read-only inventory + classification. No RLS changes, no grant changes,
  no new SECURITY DEFINER audits initiated from this block.
- `D21-D` remains **blocked** — no PoC, no directed investigation.
- `FUP-PARTITION-NAMING-01` remains hygiene, not security.

## Follow-ups (governance, not remediation)

If the weekly report shows a status flip (OK → WATCH, or a new RISK), the
diff of the CSV — including `source_hash` — is the audit trail. Any action
taken from that signal opens its own block; this file is not the place to
enumerate hypothetical remediations.
