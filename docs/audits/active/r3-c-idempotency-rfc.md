# R3-C — Idempotency RFC

> **Status:** Draft (design-only, awaiting approval)
> **Depends on:** R2 Runtime Standard RFC v1, R3-A Retry, R3-B Circuit Breaker
> **Successor blocks:** R4-prep, R4, R5
>
> **Scope discipline (non-negotiable):**
> Specification only. No code under `supabase/functions/`, no code under
> `_shared/`, no new helpers, no migrations, no signature changes, no
> prototypes. Storage schema is described only at the property level
> (columns, indexes, constraints) — the actual DDL is an R4 concern.
>
> **Closure criterion:** two independent implementations from this
> document must accept the same requests as *duplicates* and reject the
> same requests as *conflicts*, with identical observable side effects.

---

## 1. Problem

The platform performs many state-changing operations that clients
naturally retry: agent installation callbacks, webhook receivers,
billing events, invite acceptance, security-alert dispatch, agent
telemetry ingestion. Without a common idempotency primitive:

- retries (R3-A) cannot safely cover non-idempotent writes;
- webhooks from third parties can be replayed and cause double effects;
- network glitches on the front end cause duplicate mutations that RLS
  and validation cannot filter;
- there is no shared, verifiable way to answer *"did I already process
  this?"*.

R3-C defines the properties an idempotency primitive must satisfy so
that any handler performing a state-changing operation can adopt it and
so that R3-A retries can safely apply to those operations.

## 2. Use cases (in scope)

Idempotency is designed for:

1. **State-changing HTTP handlers** (`serveTenant`, `servePublic`,
   `serveAgent`, `serveInternal`) whose semantics are *at most once
   per key per window*.
2. **Third-party webhook receivers** (Stripe, provider callbacks).
3. **Internal function-to-function calls** used by R3-A retry when the
   callee performs a write.
4. **Agent ingestion endpoints** where the same telemetry batch may be
   redelivered.

## 3. Non-use cases (out of scope)

1. **Pure reads** — idempotent by nature; no primitive needed.
2. **Login / MFA / session-establishment flows** — replay of an auth
   exchange is a security concern governed elsewhere, not by this
   primitive.
3. **`serveHoneypot`** — see prior RFCs; behavioural uniformity trumps
   idempotency here.
4. **Streaming responses** — a partial-response replay is a distinct
   problem (checkpointing) not covered by this RFC.
5. **Bulk-import operations** where partial success is intended — those
   need per-item idempotency at the item layer, not at the request
   layer.

## 4. Operations that must be idempotent

Any operation in the following classes **must** adopt R3-C or provide a
documented equivalent guarantee:

- **O-A.** Any write triggered by a third-party webhook.
- **O-B.** Any write that R3-A retry may re-invoke (i.e. any
  `serveInternal` write endpoint reachable from a retriable client).
- **O-C.** Any billing state transition (creation, update, refund).
- **O-D.** Any agent-lifecycle transition (register, deregister,
  status update) triggered by the agent itself.
- **O-E.** Any user-visible action explicitly marked *at most once* in
  its handler header.

## 5. Idempotency key

- **K1.** The key is a caller-supplied string, transmitted via the
  HTTP header `Idempotency-Key` on the request, or via an explicit
  `idempotencyKey` field on internal function invocations.
- **K2.** Format: `1..255` characters, restricted to
  `[A-Za-z0-9._:-]`. Longer / other characters yield a
  `permanent` (`400`) error — never a silent truncation.
- **K3.** The **effective key** stored server-side is the tuple
  `(scope, key)` where `scope` is:
  - `tenant_id` for `serveTenant` / `serveAgent`;
  - `"public:" + route` for `servePublic`;
  - `"internal:" + route` for `serveInternal`;
  - `"webhook:" + provider` for third-party webhooks.
  This prevents cross-tenant collision on a colliding client key.
- **K4.** For `serveTenant`, keys generated by clients **must** be at
  least 16 bytes of entropy (UUIDv4 or equivalent). This is a
  documentation rule; the server does not attempt to measure entropy.
- **K5.** Absence of a key on an O-A/O-B/O-C/O-D operation is itself an
  error (`400`), except for legacy endpoints listed in an
  R4-maintained allowlist. The allowlist is expected to shrink over
  time; no new entries after R4 approval.

## 6. Time window

- **W1.** Records are retained for `retentionMs`, default **24 hours**.
  Requests outside the window are treated as *new*.
- **W2.** Different endpoint classes may declare different retention:
  - webhooks: **7 days** (providers can retry over days);
  - billing: **30 days** (audit alignment);
  - default: **24 hours**.
- **W3.** Retention is a per-scope property, not per-key. It cannot be
  extended by client hint.

## 7. Replay semantics (same key, same request)

Two requests share the same `(scope, key)` and their request payload
digests (§8) match:

- **R1.** The second request must not re-execute the operation.
- **R2.** The second request must return a response *equivalent* to
  the first. "Equivalent" means: same HTTP status, same body
  structure, same critical headers, but the response may include a
  `Idempotent-Replayed: true` marker and a fresh `X-Request-ID`.
- **R3.** If the first request is still **in-flight**, the second
  request must not run in parallel. Either it waits (bounded by
  RSC.HTMO) for the first to finish and then replays its response, or
  it responds `409 Conflict` with `code = "idempotency_in_flight"`.
  The choice is per-endpoint; both behaviours are conformant.
- **R4.** A replayed response never re-runs side effects: no
  additional DB writes, no additional outbound calls, no additional
  audit-log rows.

## 8. Conflict semantics (same key, different request)

Same `(scope, key)`, different request-payload digest:

- **C1.** The server must respond `409 Conflict` with
  `code = "idempotency_conflict"` and must not execute the operation.
- **C2.** The digest is computed over a **canonicalized** payload:
  method, path, sorted query, sorted JSON body keys, and a fixed
  subset of headers documented per endpoint. Non-canonical inputs
  (whitespace, key order) must not cause spurious conflicts.
- **C3.** From the R3-A retry perspective, `idempotency_conflict` is
  a `permanent` error (never retried).

## 9. Persistence

The primitive requires a durable store. The store's schema, at the
property level:

- **S1.** Primary key: `(scope, key)`.
- **S2.** Columns (names indicative, DDL deferred): `scope`,
  `key`, `request_digest`, `status`
  (`"in_flight" | "completed" | "failed"`), `response_status`,
  `response_headers` (subset), `response_body_ref`, `created_at`,
  `completed_at`, `expires_at`.
- **S3.** Index on `expires_at` for cleanup (§11).
- **S4.** The store is written **before** the operation executes
  (status `in_flight`) and updated **after** it finishes (status
  `completed` or `failed`) in the *same transaction* as the
  operation when the operation is a DB write; when the operation is
  a side-effecting non-DB call (external HTTP), the two writes are
  ordered but not atomic — see §12 I5.
- **S5.** Response bodies larger than a threshold
  (default **64 KiB**) are stored by reference (object storage) with
  the store keeping the reference. Small bodies stored inline.
- **S6.** The store lives in the platform schema and is subject to
  the same RLS / tenant-isolation rules as any tenant-scoped table
  when `scope` is a tenant id.

## 10. Replay behaviour on failed original

- **F1.** If the original request completed with `status = "failed"`
  and returned a `4xx` response, replays return the same `4xx` (the
  client's request was permanently wrong).
- **F2.** If it completed with `status = "failed"` and returned `5xx`,
  replays are allowed to re-execute the operation *if and only if*
  the original transaction fully rolled back. If it did not (or if
  that fact cannot be determined), replays return `409` with
  `code = "idempotency_indeterminate"`.
- **F3.** `in_flight` replays follow R3 §7.R3.

## 11. Cleanup

- **CL1.** A background job deletes rows where
  `now >= expires_at`. Cleanup is not real-time; the primitive must
  correctly treat *any* row with `expires_at < now` as absent even if
  physically still present.
- **CL2.** The cleanup job is idempotent (in the plain sense) and
  incremental; a missed run is not a data-loss event.
- **CL3.** Cleanup cadence and ownership are R4 concerns.

## 12. Invariants (verifiable)

- **I1.** For any `(scope, key)`, at most one row exists at any
  moment.
- **I2.** For any accepted request pair `(A, B)` with the same
  `(scope, key)` and matching digest, the operation runs exactly
  once — B observes A's effects and receives A's response.
- **I3.** For any request pair with the same `(scope, key)` and
  differing digest, at most one operation runs; the other receives
  `409 idempotency_conflict`.
- **I4.** A request whose key falls outside `retentionMs` is a **new**
  request; it will not receive a replayed response.
- **I5.** For non-atomic side effects (external HTTP), the store
  transitions `absent → in_flight → completed|failed`. A replay that
  observes `in_flight` never issues the external call itself.
- **I6.** No replay ever writes a second `audit_logs` row for the
  same effect (RSC.AUD is honoured by suppressing the audit call
  during replay, not by writing then deleting).
- **I7.** `idempotency_conflict` is emitted with the same
  `requestId` policy as any RC-005 error and does not leak the
  original request's body.

## 13. Integration with the Runtime Standard (R2)

- **R2.CTX** — the primitive consumes `RequestContext` for
  `requestId`, `tenantId`, and cancellation.
- **R2.ERR (RC-005)** — `409` responses use `createErrorResponse`
  with the `code`s in §7/§8/§10.
- **R2.AUD (RC-010)** — a replayed request must not double-audit;
  the primitive exposes a "replay?" signal the handler consults
  before calling `createAuditLog`.
- **R2.TEN (RC-006)** — when `scope` is a tenant id, the
  primitive's store rows are subject to tenant RLS.
- **R2.APM (RC-009)** — replay and conflict counters are additive
  to `performance_metrics`; not a schema change.

## 14. Integration with R3-A / R3-B

- **X1.** R3-A retry is safe on any O-A..O-E operation **iff** an
  idempotency key is supplied and R3-C is engaged. The retry
  primitive must forward the same key across attempts unchanged.
- **X2.** A `CircuitOpenError` (R3-B) received before the store's
  `in_flight` row is written leaves no residue. Received after the
  row is written, it results in `status = "failed"` with the
  circuit-rejection classification and §10.F2 applies.

## 15. Conformance criteria

An implementation is R3-C-conformant iff:

1. It enforces the key format in §5 and the scoping rule in K3.
2. It applies the retention rules in §6 per scope.
3. It exhibits the replay semantics in §7 and the conflict semantics
   in §8.
4. It persists per §9 with the transactional coupling rule in S4.
5. It handles failure replay per §10.
6. It satisfies invariants I1–I7, verifiable by contract tests
   simulating request pairs and interleavings.
7. It composes with R3-A and R3-B per §14.

## 16. Deferred decisions

- **D1.** Physical DDL, table name, indexes, and RLS grants —
  R4-prep / R4.
- **D2.** Storage backend for large response bodies (Storage bucket
  vs. inline JSONB with size cap) — R4-prep.
- **D3.** Whether `in_flight` waiters use polling, `LISTEN/NOTIFY`,
  or a synchronous lock — R4-prep; both R3 §7.R3 branches are
  conformant.
- **D4.** Legacy allowlist contents (§5.K5) — populated during R4
  adoption planning; not defined here.
- **D5.** Public API surface of the primitive — **out of scope for
  R3-C** by user directive.
- **D6.** Cross-region / multi-writer coordination — deferred; R3-C
  assumes a single logical store.
